# 03 — Motor Controller

A motor controller model that demonstrates artifact references, two-step
selection, a runtime write refused by a declared constraint, and the concepts
behind export-resolved output and software BOM generation.

## What it shows

- **Artifact references**: four driver binaries (`foc_driver`, `trapz_driver`,
  `absolute_encoder_driver`, `incremental_encoder_driver`) declared in
  `[artifacts]` and bound to components via `type = "artifact"` definitions
- **2-step selection**: `motor_class` selects the control mode *and* the motor
  driver artifact simultaneously; `power_rating` selects the current limit and
  gates the conditional `safety_monitor` component
- **A runtime write the model refuses**: `encoder_mode` declares
  `facet: encoder_type`, which makes it that facet's runtime handle. Writing it
  on a `high`-power session is refused, because the model declares
  `high_power_requires_absolute_encoder` — and the refusal names that rule and
  quotes its condition
- **Export-resolved output**: after compilation, the model can be resolved
  against a selection state to produce a C++ header (`config.hpp`), CMake
  build flags, and an artifact manifest — these are generated by the loader
  API's export-resolved pipeline
- **Software BOM**: the loader API can generate a full-audit BOM listing every
  resolved artifact with version, hash, and binding path

## Files

| File | Purpose |
|------|---------|
| `cue/00_definitions.cue` | 6 definitions including 2 artifact slots and a runtime-tunable gain, 3 facets, and 1 constraint |
| `cue/10_components.cue` | 4 artifacts, 4 components with overrides and a conditional component, and the facet-bound `encoder_mode` |
| `00_definitions.json`, `10_components.json` | Inheritance-resolved chunks exported from `cue/`; fed to the compiler |
| `run.sh` | Compiles, verifies, and inspects the model, resolves it, and drives the runtime through one accepted and one refused write |
| `expected/resolve.golden.json` | The resolved snapshot this selection must produce, byte for byte |

## Run it

```bash
# Build the binaries first (once):
bazel build //compiler //cfx //runtime

# Then run the example (needs `jq` on PATH):
./run.sh
```

## What to look at

After running, check `out/`:

- `compile_result.json` — 4 components, 6 definitions, 4 artifacts
- `verify_report.json` — graph integrity check
- `inspect_summary.json` — lists all components, definitions, and artifacts
- `inspect_artifact_foc_driver.json` — detail for the FOC motor driver artifact
- `inspect_motor_drive.json` — the motor_drive component with its 4 parameters
- `inspect_safety_monitor.json` — conditional component detail
- `resolve.result.json` — the resolved snapshot and its hash lineage
- `runtime_set_accepted.result.json` — the accepted `pid_gain_trim` write
- `runtime_set_refused.result.json` — the refused `encoder_mode` write:
  `status: "error"`, code `E_SELECTION_CONFLICT`, `entity_path`
  `constraints/high_power_requires_absolute_encoder`, and an `unsat_core`
  naming that rule. A refused write returns no snapshot, so the session the
  caller already holds stays valid and nothing changed

Read `runtime_set_refused.result.json` first if you only look at one file:

```bash
jq .unsat_core out/runtime_set_refused.result.json
```

## Key concepts

**Artifact references** declare versioned, hashed binary packages that the
configuration model depends on. Each artifact has a `source` URI and a
deployment `target` path:

```cue
foc_driver: {
	name:    "foc_driver"
	version: "3.1.0"
	hash:    "sha256-foc-driver"
	source:  "artifact://motor/foc_driver.so"
	target:  "/opt/configflux/motor/foc_driver.so"
}
```

Components bind artifacts through parameters whose definition has
`type: "artifact"`:

```cue
// in cue/00_definitions.cue
motor_driver_slot: {
	type:      "artifact"
	lifecycle: "construction"
	access:    "developer"
}

// in cue/10_components.cue
motor_driver: {
	inherits: "motor_driver_slot"
	value:    "foc_driver"
	overrides: [
		{condition: "motor_class == 'brushed_dc'", value: "trapz_driver"},
	]
}
```

**2-step selection** means a single selection context variable drives multiple
parameter changes. When `motor_class == 'brushed_dc'`, both the control mode
and the motor driver artifact switch together — ensuring consistency between
the algorithm and the binary it needs.

**A facet's runtime handle** is a parameter that says so. `encoder_mode`
declares `facet: encoder_type` and no value of its own:

```cue
// in cue/00_definitions.cue
constraints: {
	high_power_requires_absolute_encoder: {
		condition: "power_rating != 'high' || encoder_type != 'incremental'"
		doc:       "A high-power drive needs absolute position feedback."
	}
}

// in cue/10_components.cue
encoder_mode: {
	type:      "string"
	facet:     "encoder_type"
	lifecycle: "runtime"
	access:    "technician"
}
```

Its value *is* the facet's value, so writing it at runtime is a selection of
`encoder_type` rather than a free-form scalar poke — and the model's declared
constraints get a say. On a session resolved with `power_rating=high`, setting
`encoder_mode` to `incremental` is refused with the violated rule named. A
parameter that merely shares a facet's name declares nothing and is never
constraint-checked; `pid_gain_trim` is a plain runtime knob and is accepted
without any solver involvement.

**Export-resolved** and **software BOM** are post-compilation features in the
loader API. After compiling and resolving a model against a concrete selection
state, the API can emit:

- A C++ header with `constexpr` parameter values
- CMake build flags for conditional compilation
- An artifact manifest listing which binaries are needed
- A full-audit software BOM with versions and hashes

See the compiler scenario tests (`s4_mobile_robot`, `s5_building_hvac`) for
programmatic examples of the full export-resolved and BOM pipeline.
