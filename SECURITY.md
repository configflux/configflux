# Security Policy

## Reporting a Vulnerability

Report security vulnerabilities by emailing [security@configflux.dev](mailto:security@configflux.dev). Please do not open a public GitHub issue for vulnerabilities.

Please include:
- Description of the vulnerability and its potential impact
- Steps to reproduce
- Any suggested mitigations

You will receive a response within 72 hours. We ask that you allow us reasonable time to investigate and patch before public disclosure.

## Security Posture

Security controls for configflux — a safety-critical Rust compiler for product-line engineering.

### Unsafe Rust

- `unsafe` blocks require a `// SAFETY:` comment justifying why the invariants hold.
- Every `unsafe` block is reviewed in PR before merge.
- Prefer safe alternatives; `unsafe` is used only when there is no safe equivalent and the invariants are documented and verifiable.
- Run `cargo clippy -- -W clippy::undocumented_unsafe_blocks` to surface missing safety comments.

### Dependency Auditing

- All Rust dependencies are pinned via `Cargo.lock` (committed to git).
- Use `cargo audit` to screen for known advisories before releases.
- Use `cargo deny` to enforce allowlists for licenses and deny known-vulnerable or yanked crates.
- No dependencies may be added without reviewing their security track record.
- Bazel module hashes are pinned in `MODULE.bazel.lock`; changes to the lockfile require explicit review.

### Supply Chain

- `MODULE.bazel.lock` and `Cargo.lock` are both committed and verified in CI.
- Avoid pulling in dependencies with no upstream maintenance or security response history.
- External tools installed in the devcontainer must come from versioned, auditable sources.

### Hermetic Builds

- `bazel build` runs in a sandbox with no network access.
- Bazel sandbox is enforced; do not disable it (`--spawn_strategy=local` is prohibited except in documented infrastructure contexts).
- Build artifacts are deterministic outputs; generated files are not committed to main.

### Secrets Management

- No credentials, tokens, API keys, or private keys in source.
- CI/CD secrets are managed via environment variables injected by the pipeline, not stored in config files.

### CRA Evidence

- CRA evidence bundles are write-once outputs generated by the release gate.
- Evidence files are not committed to main; they are published as build artifacts.

### Static Analysis

- Clippy (`cargo clippy`) is part of the standard build — treat warnings as errors in CI.
- AddressSanitizer / MemorySanitizer runs are part of the release gate for native code paths.
- C++ SDK code (`sdk/cpp`, `sdk/ros2`) is linted with clang-tidy and formatted with clang-format.

### Threat Model and Residual Risks

A structured threat model, residual risk register, and deployment-side controls will be published as the deployment surface grows.

### Routine Security Screening

Security review is performed before each release covering:
- Review of changes to `unsafe` code, dependency updates, or serialization logic
- Pre-release posture review
